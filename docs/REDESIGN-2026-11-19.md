# Staff dashboard redesign — 19 November 2026

## Delivery and verification boundary

Implemented directly in the existing four-centre application. Attendance, registries, SPPB source records, approved definitions, centre routing, exclusions, personal views, permissions, reviewed imports and sync infrastructure remain in place. Earlier uncommitted SPPB simplifications were preserved. No production data was imported, no external service added and no deployment performed.

The source audit and automated checks cover the pages and shared chart families below. **Visual sign-off is incomplete:** the available browser host and native computer-use pipe were both unavailable. No screenshots, rendered breakpoint checks, browser navigation timings, real print/PDF inspection or physical-device checks were possible. DOM tests and responsive CSS are not substitutes for those checks. This delivery does not claim all 25 acceptance criteria have been visually verified.

## Reference principles

The supplied [Power BI guidance](https://learn.microsoft.com/en-us/power-bi/create-reports/service-dashboards-design-tips) supports putting the audience's decision-relevant figures first and reducing clutter. The [Sales and Marketing example](https://learn.microsoft.com/en-us/power-bi/create-reports/sample-sales-and-marketing) illustrates moving from a headline finding to a supporting view. The [Tableau examples](https://www.tableau.com/dashboard-examples) and [dashboard practices](https://help.tableau.com/current/pro/desktop/en-us/dashboards_best_practices.htm) informed question-led layouts and progressive disclosure. [Carbon chart anatomy](https://www.carbondesignsystem.com/building-blocks/data-visualization/chart-anatomy/) and [legends](https://www.carbondesignsystem.com/building-blocks/data-visualization/legends) informed concise titles, direct values and legends limited to categories actually present. No branding or proprietary assets were copied.

## Shared components and performance safeguards

New `experience.tsx` provides PageHeader, LoadingState, ErrorState and InsightCard. `experience.css` is the current global density/accessibility contract, using the existing colour/spacing tokens and responsive breakpoints. Existing ChartCard, MetricCard, ranking/trend renderers, form controls, modals, tables and drawers remain the common functional primitives rather than a competing UI library.

Dashboard and briefing GET responses can be reused in memory for up to 15 seconds, only where explicitly requested. Keys include the full URL/filter/reporting-mode scope and centre/session-context generation. Cache contents are cloned, bounded to 12 entries, never stored in localStorage and never used for individual SPPB histories or other arbitrary routes. Mutations, centre/account-context changes, reporting-mode changes and explicit Refresh clear the cache. In-flight results from an earlier write/context cannot seed the cache. New tests exercise those boundaries.

GET operations have a 30-second recoverable deadline, covering body parsing too. Write confirmations are not automatically retried or interrupted by this read deadline. Existing resumable imports remain in charge of uncertain write outcomes. The Overview module now loads separately from the initial application entry. SPPB participant/profile joins use maps instead of per-client linear searches. No persistent analytical cache, replacement aggregation, schema migration or new dependency was introduced.

## Measurements

The repeatable runner is `node scripts/measure-dashboard.mjs <output.json>`. It opens synthetic in-memory stores only: 2,400 source attendance rows, a 400-client registry, no individual SPPB assessments. Nine measured API responses follow one warm-up. Before/after captures are `redesign-20261119-before.json` and `redesign-20261119-after.json` beside this document. Timings are local loopback and sensitive to machine load; they are not hosted or browser benchmarks.

The entry JavaScript initially measured **339,832 bytes / 101,702 gzip bytes**. The final redesigned build measured **327,748 / 98,737**, about **3.6% smaller before compression**. Total route JavaScript increased **824,335 → 835,742 bytes**, and CSS increased **157,054 → 163,750 bytes**, because of the additional experience/report components. This is an initial-load tradeoff, not a claim that all assets shrank.

Final before/after medians were overview **32.30 → 19.10 ms**, full dashboard **35.02 → 31.11 ms**, briefing **37.68 → 16.38 ms**, participation **44.31 → 33.56 ms**, SPPB overview **16.71 → 16.02 ms**, and account metadata **4.26 → 7.07 ms**. Machine load was not controlled and an intermediate after run was slower on several endpoints. These observations do not establish a general backend speed improvement or prove that the redesign caused every timing difference. Both JSON files retain actual measurements and response sizes.

The runner also compared five uncached dashboard-helper calls with five calls using the new reuse option in the same isolated fixture: **5 → 1 network requests**, with warm helper median **25.725 → 0.263 ms**. This measures request avoidance and helper latency, not React rendering, browser filter completion or navigation. No claim is made that the two-second meaningful-content or 500ms browser-filter goals were achieved. Browser request counts, LCP, scrolling, layout shifts and PostgreSQL production timings remain unmeasured.

## Verification and deployment

Baseline: **333 automated tests passed**, no failures/skips. Final: **337 tests passed, zero failures/skips**, with successful lint, TypeScript checking, production build and diff checks. Focused checks exercised cache isolation, cloned results, mutation/refresh invalidation, stale centre responses, Centre Overview grants, report focus and on-demand SPPB coverage, and read deadlines versus write confirmations. The first full post-change run found an AbortError identity regression; the wrapper was corrected and both hosting tests and the final full suite passed.

Visual checks still required at **1920×1080, 1366×768, 1024×768, 768px and 375px**, independently on Overview, Programme Analysis, Participation Insights, Client Engagement, Needs, SPPB, Planning, Custom Analysis, location/domain/type views, operations, Centre Administration, Configuration/Sync, Data Management, drawers and print reports. Synthetic DOM tests cover workflows, not pixel layout. The failed browser/native discovery is the concrete blocker to full visual acceptance.

Deploy frontend and backend together through the existing hosting setup. No new SQL migration or environment variable is required for this redesign; existing multi-centre/SPPB migration prerequisites still apply. No database rows, actual member data or saved source files were changed. Live CaritaHub connectivity, actual hosted data and operational deployment were not verified.
