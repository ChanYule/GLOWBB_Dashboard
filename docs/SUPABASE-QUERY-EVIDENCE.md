# Supabase query export follow-up

The supplied CSV contained nine full snapshot statements across the legacy, GLOW Bukit Batok and SEEN Bukit Batok schemas. Together they ran 1,244 times and used 438.66 of 632.18 seconds of recorded database execution time (69.4%). The export does not provide result bytes or a deployment baseline. A snapshot can return one SQL row containing an entire dataset.

`server/postgres.js` builds the core and planning snapshots used by detailed analysis and imports. `server/data-management.js` builds the wider recovery snapshot. The legacy data review also used that recovery snapshot for its initial list. The backup query returned complete payloads on 31 calls and accounted for 11.70 seconds. The new inventory reads counts and coverage in SQL and returns 25 backup metadata rows at a time. PostgreSQL still extracts metadata from old JSON payloads for the selected page. Individual download and reviewed restore still use the original payload. Historical Data Review now obtains allocation status and counts without fetching source rows. Its preview and confirmation still use the full source fingerprint.

The legacy `glowbb` schema still holds platform identity, centre access, shared SPPB and historical allocation records. Individual centre schemas supply ordinary centre reporting. Migration preserves the legacy source, so overlap is possible and the query CSV cannot quantify it. Keep the schema. Establish provenance and compare stable IDs by approved allocation before considering retirement of any individual legacy tables.

The CSV records three large attendance and risk observation inserts and one attendance TRUNCATE. The two bulk INSERT shapes match the current PostgreSQL import writer and use ON CONFLICT DO NOTHING. The recorded row counts do not establish whether the same source records were submitted repeatedly. Current application source contains no TRUNCATE statement. The CSV alone cannot identify the caller or distinguish an older deployment from a manual operation. Current normal imports use stable IDs, incremental inserts and reviewed changes. This follow-up skips the post-write snapshot on the final batch. Intermediate batches still validate the exact source state for safe resumption. Preview staging and complex cold reports still have full-state reads and are the main remaining opportunities. No recovery history was removed.

The CSV also records 7,417 `pgbouncer.get_auth` calls. The application shares a PostgreSQL pool across its centre adapters. The statistics do not establish which clients opened those connections. Compare the next export after deployment before increasing pool concurrency. No pool or authentication changes are required for this patch.

The earlier [benchmark and SQL optimisation report](EGRESS-OPTIMISATION.md) gives the measured dashboard before/after comparison. For this follow-up the backup regression uses 26 synthetic 100 KB payloads. The first list previously selected all 2.6 MB of payloads plus the workspace snapshot. The new regression requires under 10 KB of total estimated database response bytes for a page and checks that downloading one backup still returns its exact original payload.

## Manual deployment

1. Review branch `perf/supabase-query-evidence` and push it to GitHub for a pull request. Merge it into the branch tracked by the existing Render service after review.
2. If the earlier egress update has not been applied, run `supabase/migrations/008_analytics_egress.sql` in Supabase SQL Editor after migrations 001 through 007. This follow-up adds no migration. Existing deployments with 008 can proceed directly to Render.
3. Keep the existing Render environment. The optional `ANALYTICS_CACHE_SECONDS` value is `600`. Build with `npm ci && npm run build` and start with `npm start`. Deploy the merged commit using the existing service's deploy control.
4. Check Overview, an authorised centre switch, Data Management backup paging, and Historical Data Review. Compare Supabase query statistics over similar traffic windows.
5. For rollback, redeploy the previous known-good commit from Render and revert the GitHub merge if automatic deployment is enabled. Migration 008 is additive and can stay installed. For troubleshooting the earlier dashboard SQL path, `ANALYTICS_OPTIMIZATIONS=0` bypasses that path and the main aggregate cache.
